# Журнал решений

Формат: `D-номер · дата · срез` → контекст → решение → последствия. Новые записи — в конец.

## D-001 · 2026-10-11 · S00 — Память проекта живёт в репозитории
**Контекст.** Пользователь не будет пересказывать контекст между сессиями; чат не сохраняется.
**Решение.** Три слоя: (1) `CLAUDE.md` — протокол, загружается автоматически; (2) `docs/state.json` + `tools/memory.py` — машинное состояние срезов, барьеров, допущений; (3) `docs/JOURNAL.md`, `docs/DECISIONS.md`, `docs/slices/*` — человекочитаемая история и описания. `docs/STATE.md` генерируется. `memory.py check` ловит расхождения.
**Последствия.** Закрытие среза без обновления памяти невозможно по протоколу; `finish` отказывает, пока «Итог» не заполнен.

## D-002 · 2026-10-11 · S00 — Разбиение на 30 срезов (S00–S29)
**Контекст.** План охватывает 5 этапов; сессия ограничена контекстом.
**Решение.** Срез = одна цельная проверяемая единица с границами файлов и критериями готовности. Этап 1 — 3 среза, этап 2 — 7, этап 3 — 7, этап 4 — 8, этап 5 — 4, плюс S00. Подробности: `docs/ROADMAP.md`.
**Последствия.** Срезы можно дробить (S07a, S07b), но не объединять; дробление записывать здесь.

## D-003 · 2026-10-11 · S00 — «Вместо Codex — Claude Code» (допущение A1, ждёт подтверждения)
**Контекст.** В плане Codex — это и инструмент разработки («ИИ-помощники»), и рабочий интеллект личности (через подписку Plus).
**Решение.** Разработку ведёт Claude Code. Интеллект личности скрыт за `CognitiveProvider`, поэтому провайдер заменяем; срез S08 строит изолированный исполнитель с провайдером-адаптером, S17 фиксирует итоговый выбор вместе с пользователем. До подтверждения ничего в архитектуре не закрепляется за одним провайдером.
**Последствия.** Если пользователь имел в виду замену и рабочего интеллекта на Claude, S08 переключается на Claude-адаптер без изменений остальных срезов.

**Решение.** Тесты — стандартный `unittest`; зависимости появляются в срезах, где нужны (панель — S10), с фиксацией версий.

## D-005 · 2026-10-11 · S00 — Исправления по независимому ревью
**Контекст.** Подагент-ревьюер нашёл дыры: память можно не увидеть из другой ветки; работа теряется при обрыве; `finish` не проверял зависимости и барьеры; в `brief` терялись барьеры закрытых срезов и блокировки; слабая `check`; не покрыты пункты плана (политики данных, потеря входящих >суток, условие перехода после проверки Codex, учёт расхода без API-тарифов).
**Решение.** (1) Счётчик `revision` + `memory.py sync`; барьер G10 про основную ветку. (2) `memory.py checkpoint` (WIP-коммит + push) и правило в CLAUDE.md. (3) Барьеры получили `blocks_start/blocks_finish`; `start`/`finish` их проверяют; G01/G02/G09 блокируют старт S27 (G01 — и S26). (4) `brief` показывает все открытые барьеры, «долг» закрытых срезов и причины блокировок. (5) Проверки статусов, блокировка параллельных запусков (flock), атомарная запись всех файлов, строгая `check`, непустой «Итог». (6) Недостающие пункты плана добавлены в S08, S09, S10, S27.
**Последствия.** Не исправлено сознательно: `RealRepoTest` оставлен как страж согласованности реального репозитория; `.claude/settings.json` добавлен в границы S00.

## D-006 · 2026-10-11 · S00 — PR и слияние после каждого среза разрешены
**Контекст.** Пользователь разрешил создавать PR и сливать после каждого среза (закрывает барьер G10). Оказалось, что основной веткой репозитория уже является `claude/trusting-feynman-q25phh` (единственная ветка), поэтому новые сессии клонируют её вместе с памятью.
**Решение.** Каждый срез: ветка сессии → PR в основную ветку (поле `default_branch`) → слияние `squash` при зелёных тестах и `memory.py check`. Для S00 PR невозможен (ветка сессии = основная), он «слит» самим фактом push. `memory.py sync` сравнивает ревизии всех веток `origin/*`.
**Последствия.** Основная ветка всегда несёт самую свежую память. Разрешение ограничено слиянием срезов этого репозитория; force-push, удаление веток и смена настроек требуют отдельного разрешения. Переименование основной ветки в `main` — по желанию, не обязательно.

## D-007 · 2026-10-11 · S01 — Устройство реестра требований и его проверки
**Контекст.** Срез требует реестр «план → требования → механизм → проверка → срез → свидетельство» и доказательство полноты. Проверять «полноту» по смыслу автоматически нельзя, а по номерам строк — можно.
**Решение.** (1) `requirements.toml`: записи `[[req]]` с полями среза S01 плюс `source` (раздел плана или `CLAUDE.md`) и `lines` (строки `docs/PLAN.md`); необязательные `stub_only` (проверено только на заглушке) и `waiver` (обязательно для `waived`). (2) Каждая непустая строка PLAN.md обязана входить в `lines` какого-то требования либо в явный `[[skip]]` с причиной (заголовки, шапки таблиц, вводные строки списков); `lines` обязаны лежать в разделе, указанном в `source`; диапазон — не длиннее 10 строк, чтобы одно требование не «закрывало» раздел. Если PLAN.md правится, номера строк пересматриваются — это сознательная жёсткость. (3) `verified` требует свидетельства: существующий непустой файл внутри репозитория (каталог, симлинк наружу и `..` не принимаются); для `implemented` свидетельство необязательно, но если указано — проверяется. (4) `docs/spec/plan-coverage.md` генерируется командой `reqs.py coverage --write` и сверяется тестом. (5) Требований получилось 222, а не ожидавшиеся 120–200: пункты списков и таблиц плана разнесены по отдельным записям (атомарность важнее счёта).
**Последствия.** Поле `slice` может быть списком (требование реализуют несколько срезов). Поле `check` у сценарных требований (§5.1) ссылается на файлы `scenarios/required/<slug>.toml`, которые создаст S03 — S03 обязан сверить имена и дополнить `check`. Проверки смысловой полноты остаются за независимым ревью: ревью S01 нашло несколько расплывчатых `check` (исправлены), но часть проверок конкретизируется по ходу срезов, где они реализуются. Статус `verified` у трёх записей S01 опирается на `docs/evidence/S01-requirements-registry.md` (вывод команд) и тесты; сам файл свидетельства переснимается при изменении реестра.

## D-008 · 2026-10-11 · S02 — Устройство спецификации и её привязка к реестру
**Контекст.** Срез S02 — чертежи без кода. Нужно, чтобы спецификация не расходилась с реестром требований и со схемами, а расхождение ловилось автоматически.
**Решение.** (1) Шесть документов `docs/spec/{events,state,time,provenance,permissions,envelopes}.md`; в заголовке раздела — якорь `{#имя}`, сразу под ним строка `Требования: R-…`. (2) В `mechanism` требований — ссылки `[spec: docs/spec/файл.md#якорь]`; `reqs.py validate` проверяет, что файл и якорь существуют и что связь двусторонняя (раздел перечисляет требование ⇔ требование ссылается на раздел). 103 требования привязаны к разделам. (3) Схемы `docs/spec/schemas/*.schema.json` + образцы `samples/<схема>.<имя>.valid|invalid.json`; у каждой схемы есть и допустимый, и недопустимый образец. Каталог типов событий в `events.md` (между маркерами) сверяется тестом с `enum` в `event.schema.json`. (4) Внешних зависимостей нет: `tests/schema_lite.py` — минимальная проверка подмножества JSON Schema (неизвестное ключевое слово — ошибка). (5) Ключевые семантические решения: `state_version` — одна на все группы и память; события, не меняющие состояние (`input.arrived`, запись запроса/ответа и т. п.), версию не увеличивают, поэтому поступление сообщения в паузе не «просрочивает» ответ модели; время жизни считается монотонными часами с контрольными точками (при аварии теряется не более `heartbeat_s`, всегда в сторону «жизни меньше»); архив — слой `archive` той же модели записи, не виден обычному извлечению, восстановление — только вмешательство оператора, создающее новую запись; роль определяется каналом (панель = оператор, Telegram = собеседник).
**Последствия.** Правка `PLAN.md` по-прежнему требует пересмотра номеров строк (D-007). Новые поля схем меняются вместе с образцами и текстом; тест `tests/test_spec.py` ловит рассинхрон. Тесты (`tests/test_spec.py`, `tests/test_reqs.py` — класс `SpecRefTest`) и `tests/schema_lite.py` лежат вне перечисленных «Границ файлов» среза — это сознательно (в границах не было каталога тестов, а «Проверки» среза требуют теста). Все 222 требования по-прежнему `planned/implemented/verified` как до среза: спецификация — чертёж, а не реализация механизма, статусы не повышались.

**Уточнения после независимого ревью.** Версия состояния растёт на переход (не на событие); ответ модели с несколькими предложениями проверяется на версию один раз и применяется одним переходом; повторная попытка формата — новый `request_id` с `retry_of`; к версии добавлена `epoch` (растёт при восстановлении копии); в паузе допустимы только запись входящих, системные записи, управление сеансом и вмешательства оператора, поздние результаты внешних действий записываются без применения; у модели нет права создавать события; путь к `input.read` — предложение `attend` или правило ядра; затухание считается лениво по времени жизни.

## D-009 · 2026-10-11 · правило проекта — покрытие тестами
**Контекст.** Пользователь потребовал общее правило: покрытие тестами везде не ниже 90 %, в более важных местах — выше.
**Решение.** (1) Порог по модулю, а не по среднему: ≥ 90 % строк в `src/` и `tools/`. (2) Критичные места — ≥ 98 % строк и все ветви: `StateController`, проверка версий/эпох, идемпотентность и журнал, время жизни и паузы, права и вмешательства оператора, фильтр восприятия, архив/забывание, хранилище, копии/восстановление, защита секретов. (3) Правило добавлено в `CLAUDE.md` («Жёсткие правила» и шаг закрытия среза), в реестр (R-223), в S04 (измеритель `tools/covcheck.py`). (4) Процент не заменяет качество: пустые тесты ради покрытия запрещены.
**Последствия.** До S04 измерителя нет (сторонний `coverage` не установлен), поэтому срезы S00–S03 охват не измеряют; S04 обязан сделать первый замер существующих `tools/*.py` и дописать недостающие тесты. С S04 закрытие среза проверяет пороги. Список «критичных» модулей уточняется по мере появления кода (в конфигурации измерителя).

## D-010 · 2026-10-11 · S03 — Формат сценария и связь каталога с реестром
**Контекст.** Срез S03 должен записать «экзаменационные билеты» до кода так, чтобы любой вариант системы (A/B/C, ядро S25, заглушка) прогонялся одинаково, а утверждения говорили только о наблюдаемом.
**Решение.** (1) Сценарий — TOML-файл `scenarios/<группа>/<id>.toml`, формат — `docs/spec/scenario-format.md`: предыстория, прогоны с переключателями `memory`/`motivation`, шаги из закрытого перечня, утверждения семи видов (`event`, `absent`, `order`, `chain`, `state`, `text`, `compare`) и обязательный `failure` (признак провала). «Наблюдаемое» = журнал событий, состояние, запросы к модели, результаты обычного извлечения, исходящие сообщения; типы событий сверяются с каталогом `docs/spec/events.md`. (2) Группа экспериментальных сценариев называется `experiments` (как каталог из описания среза), а не `experiment`. (3) Строки таблицы §5.1 плана присутствуют в сценариях `required` дословно (`plan_row/plan_title/plan_expected`), `validate` сверяет их с `docs/PLAN.md`; число сценариев фиксировано: 19 + 8 + 6. (4) Связь с реестром двусторонняя: требование, перечисленное в сценарии, обязано называть файл в своём `check`, ссылка на `scenarios/…toml` в `check` обязана указывать на существующий сценарий, перечисляющий это требование. Для этого в поле `check` 62 требований дописана фраза «Сценарии каталога: …»; прочие поля реестра не менялись, статусы не повышались. (5) «Каждое функциональное требование имеет сценарий или тест» проверяется так: требование перечислено в сценарии либо его `check` содержит слово «тест»/«сценарий»/«прогон» или путь `scenarios/` (грубая, но проверяемая эвристика; смысловая достаточность проверки остаётся за ревью). (6) Группы `experiments` и `motivation` ограничены 4 ключевыми решениями (`decide`) на прогон (`R-127`), утверждения помечены `technical` (исключают вариант, `R-133`) или `causal` (оценка разработчика, `R-136`); у каждого сценария мотивации есть метрика (`R-132`).
**Последствия.** Сценарии описывают ожидание, но пока ни на чём не исполняются: статусы требований `R-169…R-187` и экспериментальных остаются `planned`. Исполнитель сценариев (стенд) появится в S11, интеграционный прогон — в S25; они обязаны реализовать область `text.scope` и вид `chain` по полю `causes` журнала. Имена полей payload в `where` (например, `superseded_by`, `claim_kind`, `request_key`, `notice_level`, `reason`) и логические пути состояния (`beliefs.<тема>`, `memory.<id>`) — договорённость сценариев, которую S05–S11 обязаны либо реализовать, либо согласованно изменить вместе со сценариями. Профили временных персонажей (`persona`) создаст S11; ссылки на них в `validate` не проверяются.

**Уточнения после независимого ревью S03.** Ревьюер нашёл вакуумные и противоречащие спецификации утверждения; исправлено: (а) виды предложений в шагах `model` приведены к `envelopes.md#proposal` (добавлен `purpose` для вида запроса `reflect`), добавлены `deliveries` у `input` (повторная доставка того же обновления) и `per = "cycle"` у `event`; (б) `after`/`before` разрешены у любого вида утверждения, и инструмент проверяет, что ссылка на шаг не относится к чужому прогону; (в) лимит подписки по `time.md` даёт паузу `auth_lost`, а не `session_limit`; (г) требование «решения различаются» заменено требованием прослеживаемости там, где план требует только основания (различие вынесено в метрики `decision_divergence`); (д) авария в `pause_restart` происходит в работающем сеансе; восстановление копии оформлено вмешательством `restore_backup`; проверки «строки нет» должны подаваться на вход (тест `test_absence_assertions_are_not_vacuous`); (е) семантика `where`, логических идентификаторов, `compare`, шага `world` и допущений исполнителя описана в `scenario-format.md`. Известное ограничение: эвристика «функциональное требование имеет тест» (`TEST_MARK`) смотрит на слова в тексте `check`, поэтому 58 из 100 функциональных требований «закрыты» лишь обещанием теста; реальные тесты появятся в соответствующих срезах.

## D-011 · 2026-10-11 · S04 — Хранилище, домен и измеритель покрытия
**Контекст.** S04 закладывает фундамент: пакет `iam`, типы домена из S02, базу SQLite с журналом «только дописывать», транзакциями, замком единственного писателя и FTS5, а также измеритель покрытия для правила D-009.
**Решение.**
1. **Измеритель — `coverage.py==7.10.6`** (необязательная зависимость `dev` в `pyproject.toml`), а не стандартный `trace`: `trace` не считает ветви (а для критичных модулей правило требует все ветви) и не видит подпроцессы (тесты инструментов запускают их подпроцессами; в coverage 7.10 есть `patch = ["subprocess"]`). Контейнер эфемерный, поэтому в новой сессии перед закрытием среза нужно `pip install 'coverage==7.10.6'`; без него `tools/covcheck.py` выходит с кодом 2 и печатает команду. Пороги и список критичных модулей — `[tool.iam.coverage]` в `pyproject.toml` (сейчас критичен `src/iam/storage/*.py`). Метка исключения из замера запрещена в любом написании (covcheck ищет тем же шаблоном, что coverage.py); настройки `exclude_also`/`exclude_lines`/`omit` сверяются с разрешённым списком — единственное исключение: строка `if __name__ == "__main__":`.
2. **Архив — слой `archive` таблицы `memory_records` плюс представление `archive`**, а не отдельная таблица: спецификация (`provenance.md#layers`) требует одну модель записи для всех слоёв. Триггеры запрещают UPDATE/DELETE строк архива и смену слоя; обычный поиск (`search_memory`) архив не видит, слой нужно назвать явно.
3. **Журнал защищён самой базой:** триггеры запрещают UPDATE/DELETE, вставку поверх существующего ключа (иначе `INSERT OR REPLACE` удалил бы строку в обход триггеров DELETE — правило действует для всех защищаемых таблиц и всех их уникальных ключей; таблицы без нужды в `rowid` объявлены `WITHOUT ROWID`, чтобы скрытый `rowid` не стал лазейкой), пропуск `seq` и событие чужой личности. На соединениях ядра сторож (authorizer) вне миграций запрещает DROP/ALTER, смену опасных PRAGMA в любом регистре (`writable_schema`, `ignore_check_constraints`, `foreign_keys`, `journal_mode`, `synchronous`, `trusted_schema`, `recursive_triggers`) и прямую запись в индекс поиска `memory_fts` (только триггерами). От человека с прямым доступом к файлу это не защищает — это честная граница; целостность копий — S06.
4. **Транзакции:** WAL + `synchronous=FULL`, только явные `BEGIN IMMEDIATE`; вложенный блок — точка сохранения (SAVEPOINT): перехваченное исключение откатывает только его записи, долетевшее до внешнего блока — всё; сбой `COMMIT` откатывает транзакцию, уже откаченная SQLite транзакция не маскирует исходную ошибку. Тест аварии — 72 убийства `kill -9`: 52 ровно посреди транзакции (перед ними WAL обнуляется, кэш урезан, данные крупные — тест проверяет, что незафиксированные страницы уже лежат в файле WAL, то есть проверяется восстановление после частично записанного журнала) и 20 в случайный момент.
5. **Замок:** `flock` на файле `<база>.lock` (путь через `resolve()`: символическая ссылка на ту же базу даёт тот же замок); ОС снимает его при любой смерти процесса. Чтение (`readonly=True`) замка не берёт — для панели и отчётов.
6. **Одна личность — один файл**; создание атомарно (черновик `.<имя>.creating` → жёсткая ссылка на настоящее имя, которая не перезаписывает существующий файл): авария посреди создания не оставляет «полуличности»; вид хранилища (`permanent`/`experimental`) задаётся префиксом `per_`/`exp_`, записан в базе и неизменяем; `default_path` разводит их по каталогам `personas/` и `experiments/`. Запись памяти с `origin = simulation_event` в постоянное хранилище база не пустит.
7. **Идемпотентность:** уникальный ключ в журнале; повтор с тем же типом и `payload` возвращает исходное событие, с другим — `IdempotencyConflict` (запись `system.error` — забота StateController, S05).
8. **Снимки состояния** — одна линия: эпоха растёт только на 1, внутри эпохи версия строго растёт. Непрерывность версий (без пропусков) проверяет S05 — снимок может делаться не на каждую версию.
9. **Каталог событий в коде** (`iam.domain.catalog`) сверяется тестом с таблицей `events.md` и `enum` схемы; `Event.validate()` проверяет флаг `changes_state` и формат ключа по каталогу — это сильнее схемы.
10. **Схемы:** копии `docs/spec/schemas/*.schema.json` лежат в пакете (`src/iam/domain/schemas/`), тест требует побайтового совпадения. Мини-валидатор перенесён из `tests/schema_lite.py` в `iam.domain.jsonschema`; старый файл стал реэкспортом.
11. **Поиск по-русски:** токенизатор `unicode61` сворачивает регистр кириллицы; «ё» приравнивается к «е» на входе в индекс и в запросе. Морфологии нет («кошка» не найдёт «кошки») — если понадобится, решает S18. Синтаксис FTS из запроса не исполняется: каждое слово берётся в кавычки.
12. **Миграции:** v0 = пустой файл (поэтому «v0→v1 на заполненной базе» буквально невозможна; проверено: v0→v1 на пустой, повторный запуск на заполненной v1 и миграция-проба v1→v2 на заполненной базе с сохранением данных); каждая миграция — одна транзакция вместе с записью в `schema_version`; повтор безопасен; файл с чужими таблицами без `schema_version` не трогаем; формат новее кода — отказ. Хук `before(с, по)` вызывается перед миграцией непустой базы — сюда S06 встроит резервную копию (R-200).
13. **Ключи идемпотентности** проверяются по шаблону каталога, подстановка не содержит «:» — ключ одного типа (`out:<id>:ok`) не выдаёт себя за ключ другого (`out:<id>`).
14. **Точка часов** только растёт: меньшее значение не трогает ни время, ни отметку `updated_at`. Правило «`life_time_ms` не убывает вдоль `seq`» (`time.md#life-clock`) хранилище **не** проверяет — его обеспечивает LifeClock/StateController (S05).
**Последствия.** Выход за «Границы файлов»: `tests/domain/**` (тесты домена), `tests/test_covcheck.py` (тест измерителя, которого требует R-223), `tests/schema_lite.py` (реэкспорт вместо копии кода), `.gitignore` (файлы `.coverage*`), `docs/evidence/S04-storage.md` (свидетельство для статусов `verified`, как в S01). Независимое ревью подагентом нашло 1 блокирующую (обход неизменяемости через `INSERT OR REPLACE` в `meta`, `clock`, `memory_records`), 4 важные (регистр в PRAGMA, слабый тест аварии, замок через символическую ссылку, вложенные транзакции без SAVEPOINT) и 6 мелких находок; все исправлены с тестами. Статусы: R-147, R-198, R-223 — `verified`; R-024 — `implemented` (хранилище даёт один persona_id и одну линию снимков, полную проверку «без пропусков» закроет S05). Первый замер покрытия: все 17 модулей выше порогов, критичные модули хранилища — 100 % строк и ветвей; `tools/memory.py` — 90,8 % строк (впритык к порогу, при его правке стоит добавить тесты).

## D-012 · 2026-10-11 · S05 — Привратник состояния и часы жизни
**Контекст.** S05 строит `iam.state.StateController` (единственный писатель состояния и журнала) и `iam.clock.LifeClock` поверх хранилища S04. Спецификация (`state.md#versioning`, `time.md`, `envelopes.md#staleness`, `events.md#idempotency`) задаёт цели, но оставляет детали: как устроен «носитель» перехода, порядок проверок, что допустимо в паузе, как восстанавливаться после аварии.
**Решение.**
1. **Вход — `Proposal`:** переход (`Transition`) + исполнитель (`operator | core | model | world`) + событие-носитель + сопутствующие события той же версии. Модель событий не создаёт: её ответ принимает `receive_response`, источником события пишется `core` с пометкой `model:<провайдер>`.
2. **Носитель перехода** — событие с `payload.transition` (переход целиком) и `payload.changes` (пары «до/после» по каждой операции). По умолчанию `state.transition_applied` с ключом `trn:<transition_id>`; переходы сеанса несут `session.*`, моменты — `time.moment_due`, правки оператора — `operator.intervention`. Все события перехода получают одну новую версию; **снимок пишется на каждую версию** (`at_seq` — последнее событие перехода); версии 0 снимка нет (пустое состояние неявно).
3. **Порядок проверок `apply`:** структура (схема, тип носителя, чужая личность) → **дубль по ключу носителя** (то же содержимое — `duplicate`, исходное событие; другое — `conflict` и `system.error`) → создана ли личность → **версия `(epoch, state_version)`** (иначе `stale`, запись `proposal.stale`) → права исполнителя на тип события → допустимость события при текущем сеансе → зарезервированные носители → защищённые поля → основания (`caused_by` есть в журнале; **событие само себе основание** допускается только оператору и ядру — это корневые события вроде `persona.created`, `session.started`) → операции и конечные автоматы → пользовательские валидаторы (`add_validator`) → запись одной транзакцией (события + записи памяти + снимок). Дубль проверяется раньше версии, поэтому повтор применённого перехода — `duplicate`, а не `stale`.
4. **Отказы всегда пишутся в журнал:** `proposal.stale` (ключ `resp:<request_id | transition_id>:stale`), `proposal.rejected` (если у перехода есть `proposal_id`), иначе `system.error` (`err:<сбой>:<отпечаток>`); повтор того же отказа новой записи не создаёт. Состояние при отказе не меняется.
5. **Операции** (`paths.py`): `set` (создаёт недостающие словари), `add` (дописать в список), `remove` (ключ или значение из списка), `transition` (смена статуса **только** по конечному автомату: статусы намерений из `state.md#intentions`, состояние сеанса). Статус `done` у намерения — только при основании `action.confirmed`/`activity.completed` (правило проекта «выполнено — по подтверждённому результату»). Значения — только обычный JSON (без NaN, кортежей, множеств). Память (`group = memory`): поддержаны `add`/`set` записи по `memory_id` в той же версионной последовательности; слой `archive`, слияние и забывание — S18–S19; `simulation_event` в постоянное хранилище отклоняется заранее (а не триггером посреди транзакции).
6. **Защищённые поля:** `world_time.{session_state, session_id, life_time_ms, pause_reason, paused_at, pause_count, resume_count, moments}` и «зарезервированные носители» (`persona.created`, `session.*`, `time.moment_due`) меняются только методами контроллера (`create_persona`, `start/pause/resume/stop_session`, `schedule/cancel_moment`, `fire_due_moments`), не через `apply` — иначе журнал мог бы сообщить о сеансе, которого нет в состоянии.
7. **Пауза и остановка:** в `paused`/`stopped` допустимы `input.arrived`, `system.*`, `session.*`, `operator.intervention`, `persona.created` (таблица `time.md#sessions`); обычные переходы и запросы к модели — нет, то есть **вне запущенного сеанса состояние меняют только сеанс и оператор**. Уточнение к таблице: записи об уже летевшем запросе (`proposal.received`, `proposal.stale`, `proposal.rejected`) допустимы и в паузе — они состояние не меняют, а ответ, пришедший в паузе, обязан быть записан (E-5). **Не сделано:** «поздние результаты» внешних действий в паузе (`action.*` с `payload.late = true` и `changes_state = false`) противоречат каталогу событий (там `changes_state = true`); решает срез действий (S07/S12) вместе с каталогом.
8. **Ответ модели (`receive_response`):** формат и эхо по схеме → известный запрос (`req:<id>` в журнале) → повтор (`resp:<id>`: то же — `duplicate`, другое — `conflict`) → запись `proposal.received` → **эхо должно повторять версию запроса** (`echo_mismatch`: контекст собирался на другой версии, даже если эхо совпало с нынешней) → устаревание (`version`, `session`, `deadline`, `deadline_unknown` после перезапуска процесса) → `status`, `tool_use_detected` → каждое предложение отдельно; принятые `state_change` — **один переход** (E-10), конфликтующие по полям отклоняются поодиночке. Остальные виды предложений (`action`, `message`, `memory_write`, `intention`, `creator_request`, `no_action`, `attend`) пока получают `proposal.rejected / kind_not_supported` — их разбирает цикл (S07) и модули S18+. Всё вместе — одна транзакция: либо ответ записан и обработан целиком, либо ничего (повтор после аварии не «съест» ответ).
9. **Время жизни:** `LifeClock` измеряет монотонными часами, замораживается ровно на значении, записанном в событие паузы; события границ сеанса несут замороженное значение; значение не убывает даже при сбое источника; контроллер отказывается писать событие с меньшим `life_time_ms` (`ClockRegression`) и не стартует с часами, отстающими от журнала. `time_scale ≠ 1` — только экспериментальным личностям (R-165). **Перезапуск:** если в состоянии сеанс `running`, прошлый запуск оборвался — контроллер пишет `session.paused` с причиной `crash`; время жизни = максимум из контрольной точки (heartbeat) и последнего события, `paused_at` = время последней контрольной точки (простой считается календарным, не жизненным). Heartbeat пишет `LifeClock.heartbeat`/`StateController.tick()` по вызову цикла — отдельного потока нет (фонового опроса в ядре нет).
10. **Плановые моменты** — одноразовые записи в `world_time.moments`; `life` наступают только пока время жизни идёт; `calendar` — один раз после возобновления с `overdue_ms`. Повторяющихся моментов нет (спецификация их не требует).
11. **R-105 (единственная точка записи):** тест-«сторож» закрепляет список методов записи `Store` и статически проверяет, что их вызывают только пакеты `storage`, `state`, `clock` (последний пишет лишь контрольную точку). Новый метод записи или вызов из другого пакета ломает тест. Защита от постороннего процесса с доступом к файлу — вне модели угроз (как в R-105).
12. **Потоки:** SQLite-соединение хранилища привязано к потоку, поэтому контроллер однопоточен; «гонка двух записей» исключена замком единственного писателя (процесс) и проверкой версии (последовательные предложения на одной базе — второе `stale`).
**Последствия.** Выход за «Границы файлов»: `pyproject.toml` (список критичных модулей — `src/iam/state/*`, `src/iam/clock/*`; правило D-009), `docs/evidence/S05-state.md` (свидетельство). Схема хранилища не менялась (миграций нет). Новые обязанности следующим срезам: S06 — `system.restored` и воспроизведение через смену эпохи (`replay` сейчас отказывает на эпохе ≠ 1 с `ReplayError`); S07 — обработчики остальных видов предложений, приём входящих (`input.arrived` + строка `inbox` в одной транзакции) и поздние результаты действий; S18–S19 — операции памяти `remove/transition`, слой `archive`.

**Уточнения после независимого ревью S05.** Ревьюер нашёл 1 блокирующую, 5 важных и ряд мелких находок; исправлено с тестами: (а) **статус под автоматом нельзя обойти** операцией `set`/`add`/`remove` (в том числе записью целого родителя): после операций сравниваются статусы «до» и «после» — запись возникает только с начального статуса, статус меняется лишь операцией `transition`, запись со статусом не удаляется (`machine_bypass`); (б) права исполнителя проверяются и для сопутствующих событий, а не только для носителя (иначе модель могла бы провести поддельное `action.confirmed`); (в) `operator.intervention` — зарезервированный носитель: только через `intervene`; (г) ответ с повторяющимися `proposal_id` отклоняется целиком (`duplicate_proposal_id`), а принятые по отдельности, но не записанные вместе предложения получают `proposal.rejected`; (д) `session_id` и `moment_id` не повторяются (ключи `ses:<id>:start`, `due:<id>:1` одноразовые); (е) валидаторы получают копии состояния; (ж) `proposal.requested`/`proposal.received` пишутся только через `record_request`/`receive_response`; (з) тест эпохи при устаревании ответа. **Сознательно не сделано:** встроенные диапазоны полей групп (`0..1`, `-1..1` из `state.md` §2–8) — их задают модули-владельцы групп через `add_validator` в срезах S20–S24 (S05 даёт хук, структурные проверки и автоматы); подтверждение для `done` пока не связано с конкретным намерением (достаточно любого `action.confirmed`/`activity.completed` среди оснований) — связь уточнит S22.

## D-013 · 2026-10-11 · S06 — Копии, восстановление через смену эпохи, экспорт без секретов
**Контекст.** S06 строит страховку: снимки базы, копию перед миграцией, экспорт, восстановление, защиту от нехватки места. Тест R-105 запрещает любой модуль вне `storage/state/clock` писать в хранилище (`.append_event`, `.put_snapshot`, любое `.con`), а «нельзя менять логику StateController». Восстановление обязано открыть новую эпоху (`events.md#ids`), а воспроизведение (S05) на смене эпохи падало.
**Решение.**
1. **Снимки** — отдельным соединением «только чтение» по пути к базе + онлайн-API SQLite (`Connection.backup`); писатель не останавливается и не знает о копии. Готовится как `.<snp>.partial`, проверяется (sha256, `integrity_check`, а для актуального формата — полное воспроизведение журнала), затем одним переименованием получает имя `<личность>-<время>-<snp_…>.db`; рядом манифест `.json` (sha256, размер, личность, формат, `last_seq`, эпоха, версия). Каталог защищён `flock`. Ошибка на любом шаге удаляет недоделанное и не трогает прежние копии.
2. **Ротация** — после успешного снимка, считает только целые копии (sha256 + размер) и оставляет `keep=3` последних; повреждённая не вытесняет хорошие и **не удаляется молча** (попадает в `corrupt`, CLI возвращает код 1). Поэтому в каталоге с повреждённой копией файлов может быть больше трёх — это видимо намеренно.
3. **Копия перед миграцией** — `migration_hook` подключается к `before` мигратора (`Store.open(before_migrate=…)`, `open_for_write`): всегда делается **новая** проверенная копия в `<каталог>/pre-migration/` (своя ротация до 3, чтобы копии перед миграциями не вытеснялись обычными). Копия не удалась (нет места, база повреждена) — исключение, миграция не начинается.
4. **Запись о копии** — `system.backup_created` пишет контроллер (`record_event`), если он передан в `create_backup`; в самой копии этого события нет (оно после неё). CLI `backup` на свободной базе открывает контроллер с `recover=False` (копия не должна превращаться в «восстановление после аварии»); на занятой базе делает только снимок и говорит об этом.
5. **Восстановление** — только в **отдельный каталог**, живая база не открывается на запись и не заменяется. Порядок: проверка копии → черновик `.<личность>.db.restoring` (копия через backup API) → открытие (возможная миграция формата — на копии) → проверка воспроизведения (`checked_on_copy`) → `mark_restored` → повторная проверка → жёсткая ссылка на настоящее имя (не перезаписывает) → черновик убран. Целевая база уже есть (в том числе это живая база) — отказ. Причина обязательна (это вмешательство оператора). Копия без единого события восстановлению не подлежит.
6. **Эпоха** — новый модуль `iam.state.restore.mark_restored` (выход за «Границы файлов», он нужен, потому что писать в журнал можно только из `iam.state`; логика `StateController` не менялась). В одной транзакции: `operator.intervention` (`kind=restore_backup`, открывает эпоху `E+1` на той же версии), `system.restored` (`causes` → вмешательство; `from_epoch/to_epoch`, `restored_to_seq`, `checked_on_copy`, `lost_seq_from/to` если известны, сведения о копии) и снимок `(E+1, версия)` с тем же состоянием (если переходов не было — сначала исходный `(1, 0)`). `StateController` на такой базе живёт в новой эпохе, ответы моделей прежней эпохи устаревают обычной проверкой `(epoch, version)`. События после точки копии в восстановленную базу не попадают.
7. **Воспроизведение через смену эпохи** (`iam.state.replay`, выход за границы, ожидалось в S05): смена эпохи допустима только как `+1` на вмешательстве `restore_backup` на той же версии состояния; `system.restored` закрепляет её и даёт шаг воспроизведения со сверкой снимка `(эпоха, версия)`; метки `snapshots_at` теперь по паре (эпоха, версия). Любая другая смена эпохи — по-прежнему `ReplayError`. Текст «нет снимка версии N» для эпохи 1 не изменился.
8. **Экспорт** — один zip: `manifest.json` + JSON-строки по таблицам (личность, журнал, снимки, память всех слоёв **включая архив** — это полная копия содержания для оператора, не для обычного извлечения, входящие, исходящие, часы). Чтение одной согласованной транзакцией. Строки данных редактируются сканером (`[СЕКРЕТ УДАЛЁН]`, число замен по видам в манифесте), готовый пакет **перепроверяется целиком** (текст и разобранный JSON); найден секрет — файл не создаётся (`SecretFound`, в сообщении вид и место, не значение). Экспорт — для переноса и чтения, не для точного восстановления.
9. **Сканер секретов** — шаблоны высокой точности (токен бота Telegram, `sk-…`, GitHub, AWS, Slack, JWT, закрытый ключ, `Bearer …`), присваивания «слово-секрет = значение» (только для данных личности: в документах репозитория такие примеры встречаются), «канарейки» (точное вхождение в сыром, JSON-экранированном и base64-виде) и секреты окружения (имя содержит TOKEN/SECRET/PASSWORD/API_KEY/AUTH, значение ≥ 8 знаков). Секреты в аргументы CLI не передаются: `--secret-env ИМЯ` называет переменную. Тест проходит сканером по файлам, отслеживаемым git (R-219).
10. **Нехватка места** — `SpaceGuard` (запас = размер записи + резерв 64 МиБ, из резерва оплачивается запись остановки) проверяется перед копией, экспортом и восстановлением; `guarded_call(controller, guard, fn)` проверяет запас перед записью личности и при `NotEnoughSpace` или настоящем «диск полон» (`SQLITE_FULL`, ENOSPC) записывает `system.error`(`disk_full`) и останавливает сеанс (каждый шаг сам может упереться в нехватку — тогда откатывается целиком); исключение пробрасывается всегда. Встраивание `guarded_call` в цикл сеанса — S07/S10; хаос-набор — S10.
11. **CLI** `iam backup|export|restore|verify` (`src/iam/cli.py`, строка `[project.scripts]` в `pyproject.toml` — выход за границы, иначе команды нечем вызвать); `python3 -m iam.cli …`. Коды выхода: 0 — хорошо, 1 — проблемы/отказ, 2 — неверный запуск.
