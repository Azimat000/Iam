# S01 — Реестр требований

**Этап:** 1 (Спецификация) · **Зависит от:** S00 · **Требования:** создаёт реестр

## Простыми словами
План — это связный текст, а проверять нужно по пунктам. Мы превращаем каждое обещание плана («не повторять просьбу», «забывание не восстанавливается из архива», «не больше 10 обращений») в строку таблицы: номер, откуда взято, какой частью системы обеспечивается, чем докажем и в каком срезе будет сделано. В конце проекта эта таблица — наш «акт приёмки»: если у строки нет свидетельства, мы не вправе говорить «готово».

## Что делаем
- `requirements.toml`: записи `[[req]]` с полями `id` (R-001…), `source` (раздел плана), `text`, `kind` (functional / constraint / process / quality), `mechanism` (интерфейс/модуль), `check` (сценарий или тест), `slice` (где реализуется), `status` (planned / implemented / verified / waived), `evidence` (путь/ссылка, пусто пока нет).
- Разобрать PLAN.md построчно: таблицу решений §1, правила §2 (каждое «разделяем/сохраняем/не…»), эксперименты §3, этапы §4, 19 сценариев и ограничения §5, 7 критериев готовности. Ожидаемо 120–200 записей.
- `tools/reqs.py`: `validate` (поля, уникальность, ссылки на существующие срезы), `report` (сводка по статусам и срезам), `unverified` (список без свидетельств).
- `docs/spec/plan-coverage.md`: таблица «раздел плана → ID требований» (доказательство полноты).
- Показ сводки требований в `memory.py brief`.

## Границы файлов
Можно: `requirements.toml`, `tools/reqs.py`, `tools/memory.py` (только `brief`), `tests/test_reqs.py`, `docs/spec/plan-coverage.md`, `docs/DECISIONS.md`, файл среза.
Нельзя: `src/**`.

## Проверки
- `reqs.py validate` проходит; у каждого требования есть mechanism и check (поля непустые, кроме kind=process, где check — процедура).
- Каждый абзац/пункт PLAN §1–§5 отражён в plan-coverage.md; пропуски перечислены явно.
- Независимый подагент ищет пропущенные обязательства в плане — найденное добавлено.
- Тесты `reqs.py` на корректных и нарушенных файлах.
