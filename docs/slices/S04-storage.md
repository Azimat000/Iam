# S04 — Каркас: проект и хранилище

**Этап:** 2 (Технический каркас) · **Зависит от:** S03 · **Требования:** транзакционность, журнал, один управляющий процесс, FTS

## Условие завершения и переход (D-053)

Запрет изменения журнала, единственный писатель, миграции пустой/заполненной базы и русский FTS проверены; не менее 50 прерываний транзакций не оставляют частичных данных; введён замер покрытия по модулям.

**Подтверждение:** Тесты хранения/миграций/аварий, отчёт покрытия с порогами D-009.

**После приёмки:** S05; S07 также использует этот фундамент. Не требовать готовой личности.

**Предел повторов:** [общий протокол и специальные бюджеты](../COMPLETION.md). Контракт уточняет раздел «Проверки»; прежний ход работы и итоги ниже остаются историей, а не новым требованием повторять эксперименты.

## Простыми словами
Фундамент: пакет Python и база SQLite — «сейф», где хранится всё. Две главные идеи. Первая: журнал событий только дописывается, ничего в нём нельзя ни стереть, ни изменить (чтобы всегда можно было восстановить, что происходило). Вторая: транзакции — любое изменение либо записывается целиком, либо не записывается совсем, даже если питание пропало посреди операции. Плюс замок: одновременно личностью может управлять только один процесс.

## Что делаем
- `pyproject.toml` (Python ≥ 3.13, без внешних зависимостей), пакет `src/iam/`.
- `iam.domain`: типы из спецификации S02 (dataclass-ы), сериализация, валидация по JSON-схемам.
- `iam.storage`: схема v1 + мигратор с таблицей версий; таблицы: события (append-only, запрет UPDATE/DELETE триггерами), снимки состояния, записи памяти + FTS5, входящие/исходящие (inbox/outbox), архив; WAL; хелпер транзакций; файловый замок единственного писателя.
- `tools/covcheck.py`: измеритель покрытия строк тестами по модулям (стандартный `trace` или `coverage.py` с зафиксированной версией — выбор записать в DECISIONS), пороги из D-009 (≥ 90 %, критичные модули ≥ 98 %, список критичных в файле конфигурации); первый замер покрывает уже существующие `tools/*.py`, недостающие тесты дописать.
- Каждая личность — отдельный файл базы (основа для разделения экспериментов и постоянной жизни).

## Границы файлов
Можно: `tools/covcheck.py`, `pyproject.toml`, `src/iam/domain/**`, `src/iam/storage/**`, `tests/storage/**`, `requirements.toml` (статусы).
Нельзя: `src/iam/state`, `cycle`, `providers`, `telegram`, `panel`.

## Проверки
- Тест: UPDATE/DELETE по журналу событий отклоняются базой.
- Тест аварии: процесс убит (`kill -9`) посреди транзакции → база согласована, частичных записей нет (≥50 итераций).
- Тест замка: второй управляющий процесс не получает доступ.
- Миграции: v0→v1 на пустой и на заполненной базе; повторный запуск безопасен.
- FTS5 находит по русскому тексту (нормализация регистра).

## Итог
**Сделано.** `pyproject.toml` (Python ≥ 3.13, без зависимостей ядра; `dev` = `coverage==7.10.6`, настройки замера и пороги D-009). Пакет `src/iam`:
- `iam.domain` — идентификаторы, каталог 45 типов событий (флаг состояния и шаблон ключа идемпотентности), dataclass-ы `Event`, `MemoryRecord`, `Transition`/`Op`, `Source`, `Link`; канонический JSON; проверка по JSON-схемам (схемы — копии `docs/spec/schemas` в пакете, валидатор перенесён из `tests/schema_lite.py`). Конверты request/response/proposal пока проверяются как словари (классы — S07).
- `iam.storage` — схема v1 и мигратор с `schema_version` (хук «перед миграцией» для копии S06); таблицы: журнал событий (только дописывается: UPDATE/DELETE/REPLACE отклоняет база, `seq` подряд, одна личность), снимки состояния (неизменяемы, одна линия по эпохе и версии), записи памяти одной моделью + FTS5 (архив — слой `archive`, неизменяем, обычному поиску не виден; «ё=е», регистр не важен), входящие/исходящие (дедупликация по каналу и внешнему id; автомат статусов отправки), точка часов; WAL + `synchronous=FULL`; транзакции с точками сохранения; сторож соединений (DDL, опасные PRAGMA, прямая запись в индекс); замок единственного писателя (`flock`); проверка окружения (Python, FTS5); `Store` — одна личность = один файл, атомарное создание, `personas/` и `experiments/` раздельно, `simulation_event` в постоянное хранилище не попадает.
- `tools/covcheck.py` — замер по модулям под coverage.py (с подпроцессами), пороги из `pyproject.toml`, запрет метки исключения и расширенных исключений.
Решение D-011. Статусы: R-147, R-198, R-223 — `verified`; R-024 — `implemented`.

**Как проверено.** `python3 -m unittest discover -s tests` — 255 тестов зелёные; `tools/covcheck.py` — все 17 модулей выше порогов, критичные модули хранилища 100 % строк и 100 % ветвей; `reqs.py validate`, `memory.py check` зелёные (вывод — `docs/evidence/S04-storage.md`). Проверки среза: UPDATE/DELETE/REPLACE/UPSERT по журналу, снимкам, архиву, `meta`, часам, входящим отклоняются «сырым» SQL (`tests/storage/test_journal.py`); 72 убийства `kill -9` — 52 ровно посреди транзакции с незафиксированными страницами уже в WAL, 20 в случайный момент — база каждый раз целостна, переходы либо целиком, либо нет (`test_crash_lock.py`; что проверка ловит частичные записи, ревьюер подтвердил, подменив транзакцию пустышкой); второй процесс (и та же база через символическую ссылку) получает отказ, после `kill -9` владельца замок свободен; миграции v0→v1 на пустой, повтор на заполненной, проба v1→v2 на заполненной, откат сломанной миграции, параллельный мигратор, чужая и слишком новая база (`test_migrations.py`); FTS5 по-русски без учёта регистра и с «ё» (`test_store.py`). Тесты измерителя — на искусственных отчётах и полным прогоном на пробном проекте (`tests/test_covcheck.py`). Независимое ревью подагентом: 1 блокирующая, 4 важные, 6 мелких находок — все исправлены с тестами (D-011, «Последствия»).

**Не сделано / ограничения.** Защита журнала действует внутри SQLite и на соединениях ядра; человек с прямым доступом к файлу может её снять (`DROP TRIGGER` с обычного соединения) — защита копий и проверка целостности в S06. Хранилище не проверяет непрерывность версий состояния и неубывание `life_time_ms` вдоль `seq` — это StateController/LifeClock (S05), поэтому R-024 — `implemented`, не `verified`. Морфологии в поиске нет («кошка» не найдёт «кошки»). Запись `system.error` при конфликте ключа идемпотентности — обязанность S05 (хранилище бросает `IdempotencyConflict`). `tools/memory.py` покрыт на 90,8 % — впритык к порогу.
