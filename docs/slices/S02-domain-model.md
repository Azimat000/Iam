# S02 — Модель домена: события, состояние, время, права

**Этап:** 1 (Спецификация) · **Зависит от:** S01 · **Требования:** состояние, время, восприятие, происхождение, права

## Простыми словами
«Словарь и чертежи» системы. Прежде чем писать код, фиксируем: какие бывают события (пришло сообщение → замечено → прочитано — это три разных события), из чего состоит «состояние» личности, как считается её собственное время (стоит, когда программа остановлена), откуда берётся каждая информация (увидела сама / сказал человек / знание модели / выдумала / воображение / симуляция) и кто что вправе делать (знать, хотеть и иметь право — разные вещи). Это ещё не программа, а точные определения, на которые потом опираются тесты.

## Что делаем
- `docs/spec/events.md`: каталог типов событий, стадии восприятия, идентификаторы, ключи идемпотентности.
- `docs/spec/state.md`: компоненты состояния из плана §2 (черты, эмоции, убеждения, отношения, цели/намерения, предпочтения, самомодель, мир, время), версионирование.
- `docs/spec/time.md`: календарное и жизненное время, правила пауз и возобновления, плановые моменты.
- `docs/spec/provenance.md`: три слоя памяти (архив / доступная / интерпретации), типы происхождения, правила «сообщил X ≠ X истинно», независимость источников.
- `docs/spec/permissions.md`: роли (оператор, личность, внешний собеседник), реестр возможностей, состояния «знает / хочет / вправе», вмешательства оператора.
- `docs/spec/envelopes.md`: запрос/ответ модели с идентификатором и версией состояния, правило устаревания, формат предложения решения.
- `docs/spec/schemas/*.json`: JSON Schema для события, предложения, записи памяти, запроса/ответа.
- Привязать каждый раздел к ID требований (`mechanism` в requirements.toml указывает на раздел спецификации).

## Границы файлов
Можно: `docs/spec/**`, `requirements.toml` (поля mechanism/check), `tools/reqs.py` (проверка ссылок на спецификацию), файл среза.
Нельзя: `src/**`.

## Проверки
- Все 8 групп состояния из §2 и все 9 видов памяти из таблицы §2 присутствуют в спецификации.
- Все `schemas/*.json` — валидный JSON; тест проверяет корректность образцов.
- `reqs.py validate` подтверждает: каждая ссылка `mechanism` указывает на существующий раздел spec.
- Подагент-ревьюер ищет противоречия между разделами спецификации.

## Итог
**Сделано.** Шесть документов `docs/spec/{events,state,time,provenance,permissions,envelopes}.md` (36 размеченных разделов с якорями `{#…}` и строками «Требования:»); шесть JSON-схем `docs/spec/schemas/*.schema.json` (событие, переход состояния, запись памяти, предложение, запрос, ответ) и 28 образцов (допустимых и недопустимых). Каталог из 45 типов событий, три стадии восприятия с уровнями уведомления N1/N2, восемь групп состояния, три слоя и девять видов памяти, семь типов происхождения, правила независимости источников, два времени (календарное и жизни) с правилами пауз, роли и вмешательства оператора, устаревание ответа модели по паре `(epoch, state_version)`. 111 требований привязаны к разделам через `[spec: файл.md#якорь]` в `mechanism`.

**Как проверено.** `python3 -m unittest discover -s tests` — 100 тестов зелёные (в т. ч. `tests/test_spec.py`: образцы против схем, 8 групп, 9 видов, 7 происхождений, каталог событий = enum схемы, группы = enum перехода; `tests/test_reqs.py::SpecRefTest`: ссылки и двусторонняя связь). `reqs.py validate`, `coverage --check`, `memory.py check` зелёные. Независимое ревью подагентом нашло 15 групп замечаний (версия на переход, а не на событие; пакет предложений в одном ответе; повторная попытка с новым `request_id`; heartbeat и монотонность `life_time_ms`; `epoch` при восстановлении копии; допустимые события в паузе; путь к `input.read` через предложение `attend`; определение «технического архива» и восстановление; права и `capability_id`; `claim_kind` и счёт независимых оснований; согласование схем и текста) — исправлены; тесты усилены.

**Не сделано / ограничения.** Спецификация — чертёж: ни один статус требования не повышен (ни `implemented`, ни `verified`). Схемы проверены собственным минимальным валидатором подмножества JSON Schema (`tests/schema_lite.py`), не эталонным `jsonschema`: отдельные ключевые слова (oneOf, patternProperties и т. п.) не поддержаны и не используются. Формулы затухания, пороги (`min_bases`, `restore_availability`, `max_rerequest`, `pause_grace_ms`) — начальные значения настроек, их калибровка в срезах S19–S24. Тексты «Требования:» ведутся вручную, а проверяются лишь на двустороннюю согласованность с `mechanism`.
