# Спецификация: события

Статус: S02. Источник: `docs/PLAN.md` §2.1, §2.2, §2.8, §5.1. Машинная схема: `schemas/event.schema.json`.
Каждый раздел с якорем `{#...}` связан с требованиями строкой «Требования:» — `tools/reqs.py validate` проверяет связь в обе стороны.

Всё, что происходит с личностью и вокруг неё, записывается как **событие** в неизменяемый журнал (технический архив). Событие — факт «что-то произошло», а не вывод «что это значит»: смысл — отдельный слой (`provenance.md`).

## 1. Идентификаторы {#ids}

Требования: R-024, R-107

- `persona_id` — один на личность на всё время жизни (`per_` + 8–40 символов `[A-Za-z0-9]`). Экспериментальные персонажи имеют id с префиксом `exp_` и никогда не попадают в постоянное хранилище.
- `event_id` — `evt_…`, уникален глобально, непрозрачен (порядок по нему не определяется).
- `seq` — целое, монотонное, без пропусков в пределах личности; присваивается журналом **при фиксации** (у ещё не записанного события `seq = null`). Порядок событий — только по `seq`.
- Прочие идентификаторы: `req_…` (запрос к модели), `prop_…` (предложение), `act_…` (действие), `mem_…` (запись памяти), `trn_…` (переход состояния), `int_…` (намерение), `opr_…` (вмешательство оператора, оно же `intervention_id`), `cap_…` (возможность), `ses_…` (сеанс), `cyc_…` (цикл: один проход «событие → … → обновление памяти», `cycle_id`), `inp_…` (входящий элемент, `input_id`), `mom_…` (плановый момент, `moment_id`), `crq_…` (просьба оператору), `snp_…` (снимок/копия, `snapshot_id`). Шаблон: `^[a-z]{2,4}_[A-Za-z0-9]{8,40}$`.
- `epoch` — целое, начинается с 1, увеличивается на 1 при восстановлении из копии (`system.restored`). Вместе с `state_version` образует полную версию: `(epoch, state_version)`. Это не даёт ответу модели, выданному до отката, совпасть по номеру версии с состоянием после отката. Внутри эпохи `seq` и `state_version` только растут; после отката нумерация продолжается от восстановленной копии, а разрыв отмечается событием `system.restored` (в нём `lost_seq_from`/`lost_seq_to`, если известны).
- Время в событии — всегда пара: `occurred_at` (календарное, UTC, ISO 8601) и `life_time_ms` (время жизни личности, см. `time.md`). Для события, пришедшего из внешнего мира в паузе, `life_time_ms` — значение на момент паузы.

## 2. Конверт события {#event-envelope}

Требования: R-037, R-045, R-105

Поля (полная схема — `schemas/event.schema.json`):

| Поле | Смысл |
|---|---|
| `event_id`, `persona_id`, `seq` | см. раздел 1 |
| `type` | тип из каталога (раздел 3) |
| `occurred_at`, `life_time_ms` | календарное время и время жизни |
| `source` | `{kind, ref}`: кто породил событие (`operator_panel`, `external_person`, `persona`, `core`, `model`, `world`, `system`, `receiver`) |
| `causes` | список `event_id`, из-за которых возникло это событие (причинная цепочка) |
| `idempotency_key` | ключ дедупликации (раздел 5), уникален в пределах личности |
| `state_version` | версия состояния, **в которой** событие применено; у событий, не меняющих состояние, — версия на момент записи |
| `changes_state` | `true`, если событие входит в переход состояния (само является переходом или создано им). Версию увеличивает **переход** (один раз, на 1), а не каждое событие: все события одного перехода записываются с одной и той же новой версией и общим `payload.transition_id` |
| `payload` | данные по типу события |
| `schema_version` | версия формата события |
| `epoch` | эпоха (после восстановления копии увеличивается, см. раздел 1) |

Правила:

1. **Журнал только дописывается.** Событие нельзя изменить или удалить; исправление — новое событие, ссылающееся на старое через `causes`.
2. Событие, пришедшее снаружи, записывается **до** любого воздействия на состояние (`changes_state = false` для самой записи поступления).
3. Модель не создаёт события напрямую: она возвращает предложение (`envelopes.md`), а событие записывает ядро.

Пояснения:

- Стадии получения сообщения — три **разных** события (`input.arrived` → `input.noticed` → `input.read`), см. раздел 4.
- Запись об **успешном действии** (`action.confirmed`) возникает только от подтверждающего источника (мир или канал), никогда от модели и никогда от самого `action.attempted`. Пока нет подтверждения, воспоминание «я сделала» не создаётся (`R-199`, `R-222`); если подтверждения не пришло — `action.unknown_outcome`, а не успех.
- `memory.retrieved` не меняет состояние, но пишется в журнал: именно по нему видно, какой опыт участвовал в решении (трасса, срез S11).
- Ответ оператора на просьбу приходит как обычное входящее сообщение (`input.arrived` → … → `input.read`); событие `creator.reply` создаётся ядром **после** `input.read`, поэтому проходит стадии восприятия и в паузе не возникает.
- `system.rejected_sender` фиксирует сообщение от неизвестного отправителя (не из белого списка): содержимое не сохраняется как опыт и не попадает в восприятие.
- События создаёт только ядро, приёмник, мир и оператор; **модель событий не создаёт** — её ответ записывает ядро как `proposal.received`.
- `operator.intervention` — единственный тип для технических правок оператора (подробности — `permissions.md#interventions`).
- События запускаются **по значимым изменениям**, а не по тактам: нет типа «такт»/«опрос». Цикл (срез S07) стартует от события из этого каталога; фонового опроса модели нет.

## 4. Стадии восприятия {#perception-stages}

Требования: R-012, R-035, R-037, R-038, R-039, R-175

Для каждого входящего элемента (`input_id`, обычно сообщение) определён конечный автомат:

```
            (приёмник)         (внимание)            (решение личности)
  [нет] ──► arrived ──────────► noticed ───────────► read
                                    │
                                    └────────────► ignored  (решила не открывать сейчас)
```

| Стадия | Что означает | Что видит личность | Кто и когда может создать |
|---|---|---|---|
| `arrived` | приёмник сохранил элемент | ничего | приёмник, всегда, в том числе в паузе; не вызывает модель |
| `noticed` | внимание допустило элемент до сведения | только уровень уведомления (ниже) | только при активном сеансе (время жизни идёт) |
| `read` | личность решила открыть и содержимое передано | всё содержимое | только при активном сеансе, только после `noticed`, только по принятому предложению/решению внимания |
| `ignored` | личность решила не открывать (сейчас) | ничего нового | как `read`, только после `noticed`; не окончательно: позже возможен `read` |

**Уровни уведомления** (`notice_level` в `input.noticed`):

| Уровень | Что сообщается | Содержимое |
|---|---|---|
| `N1` | «есть новое» (только количество) | скрыто |
| `N2` | кто и когда (отправитель, календарное время поступления, тип канала) | скрыто |

Другого уровня нет: следующий после `N2` — стадия `read`. Допускается повышение `N1 → N2` (новое событие `input.noticed` с другим уровнем).

Правила:

- **P-1.** Содержимое элемента в стадии `arrived`/`noticed`/`ignored` не входит ни в один запрос к модели, ни в рабочую память, ни в эмоциональную оценку. Построитель контекста берёт только те элементы, для которых есть `input.read`. Количество `N1` может влиять на внимание, но с насыщением (вклад уведомлений ограничен сверху, `R-042`).
- **P-2.** Событие «я прочитала» (`input.read`) не может иметь `life_time_ms` меньше, чем у предшествующего `input.noticed`, и не может быть создано, пока сеанс на паузе (`R-035`).
- **P-3.** Повторная доставка того же элемента (`idempotency_key` = `rx:<канал>:<внешний id>`) стадию не создаёт заново (раздел 5).
- **P-4.** Метаданные N2 (отправитель, время) не раскрывают содержимое; тема/превью — это содержимое, их в N2 нет.
- **Путь к `read`.** Решение «открыть» принимает внимание: либо правилами ядра, либо через предложение вида `attend` с выбором `event`/`dialogue` и ссылкой на `input_id` (`envelopes.md#proposal`); ядро проверяет его и записывает `input.read`. Уровни N1/N2 попадают в запрос к модели как элементы контекста со слоем `notice` без содержимого.
- Для элементов, пришедших не от людей (результат действия мира), стадий восприятия нет: они приходят как `activity.completed`/`action.*`.

## 5. Ключи идемпотентности {#idempotency}

Требования: R-161, R-162, R-183, R-188, R-189

- У каждого события есть `idempotency_key` (формат — в столбце «Ключ» каталога). В пределах личности ключ уникален (уникальный индекс в журнале).
- Запись события с уже существующим ключом **не создаёт нового события**: возвращается исходное событие, состояние не меняется второй раз. Это защита от повторов Telegram (`update_id`), повторной доставки ответа модели, повторного результата действия и повторной обработки после сбоя.
- Ключ строится из внешнего или внутреннего **натурального идентификатора**, а не из времени и не из содержимого: два разных одинаковых сообщения — два события; одно сообщение, доставленное дважды, — одно.
- Повтор с тем же ключом, но другим `payload`, — ошибка целостности (`system.error`), оригинал не перезаписывается.
- Повтор результата или «старый ответ» (ответ с устаревшей версией состояния или с уже принятым `request_id`) не применяются второй раз: `proposal.stale` / дедупликация по `resp:<request_id>` (`envelopes.md#staleness`).
- Неопределённый исход отправки (`message.out_unknown`) — отдельное состояние, не повторяется бесконечно: повторная отправка допускается не более `max_resend` раз (настройка, по умолчанию 1) и только по явному решению оператора или с изменением обстоятельств; каждый повтор получает свой `action_id`.
