# Спецификация: формат сценария проверки

Статус: S03. Проверка формата и каталога: `python3 tools/scenarios.py validate`. Сценарии лежат в `scenarios/<группа>/<id>.toml`.

Сценарий — «экзаменационный билет»: что подаём на вход, какие утверждения о **наблюдаемом** (журнал событий, состояние, запросы к модели, исходящие сообщения) должны выполниться и что считается провалом. Билет не знает, какой вариант системы его проходит (вариант A/B/C, ядро S25, заглушка): прогон одинаковый для всех. В утверждениях нет слов «модель должна подумать»; проверяется только то, что видно в записях (`docs/spec/events.md`, `state.md`, `provenance.md`).

## 1. Группы и количества

| Группа (каталог) | Сколько | Откуда | Где прогоняется |
|---|---|---|---|
| `required` | 19 | таблица плана §5.1, одна строка — один сценарий | ядро, срез S25 (`R-169…R-187`) |
| `experiments` | 8 | план §3.2: разный опыт, исправление, повтор критики, непрочитанное, нет сообщений, новый интерес, нет инструмента, отказ | стенд S11–S14, 3 варианта × 2 повторения (`R-126`) |
| `motivation` | 6 | план §3.3: возникновение интереса, возврат к незавершённому, потеря интереса, неудача, переключение, возможность ничего не делать | S15 (`R-132`) |

Имя файла = `id` сценария = значение `id` внутри файла. Для `required` имена заданы реестром требований (поле `check` у `R-169…R-187`).

## 2. Поля сценария (верхний уровень)

| Поле | Обязательно | Смысл |
|---|---|---|
| `format` | да | версия формата, сейчас `1` |
| `id`, `group`, `title`, `summary` | да | идентификатор, группа (= каталог), короткий заголовок, описание простыми словами |
| `requirements` | да | список ID требований, которые сценарий проверяет (все должны существовать в `requirements.toml`) |
| `failure` | да | признак провала одной-двумя фразами: что именно в записях означает «не прошло» |
| `plan_row`, `plan_title`, `plan_expected` | только `required` | номер строки таблицы §5.1 (с 1) и её два столбца **дословно** — инструмент сверяет их с `docs/PLAN.md` |
| `persona` | нет | имя профиля временного персонажа (`scenarios/personas/*`, создаётся в S11; `any` — любой) |
| `seed` | нет | семя для воспроизводимости |

## 3. Предыстория `[[background]]`

То, что есть до начала: записи памяти, убеждения, намерения, отношения, мир, возможности, настройки. Поля: `kind` (`memory`, `belief`, `intention`, `relation`, `world`, `capability`, `config`), `text` (что именно, словами), необязательные `id`, `origin` (один из семи типов происхождения, `provenance.md`), `run` (только для этого прогона), `note`.

`id` предыстории — **логическое имя**: путь `memory.<id>…`, `intentions.<id>…` в утверждениях о состоянии ссылается на неё. Для убеждений логическое имя — тема (`beliefs.<тема>`), её задаёт сценарий.

## 4. Прогоны `[[run]]` и переключатели

Без `[[run]]` сценарий идёт одним прогоном. Если нужно сравнить две ситуации, объявляются **два и больше** прогонов (один не допускается):

```toml
[[run]]
id = "mem_off"
switches = { memory = "off" }     # memory / motivation: "on" | "off"
```

Шаг, утверждение и предыстория с полем `run` относятся только к этому прогону; без `run` — ко всем. Переключатель `memory = "off"` обязан убрать прошлый опыт из контекста запроса; `motivation = "off"` — убрать мотивацию из выбора (`R-138`). Если прогонов несколько, нужно хотя бы одно утверждение `compare`.

## 5. Шаги `[[step]]` (входные события)

Каждый шаг: уникальный `id`, `kind`, необязательные `run`, `note`. Порядок в файле — порядок выполнения.

| `kind` | Поля | Что происходит |
|---|---|---|
| `session` | `action`: `start`/`pause`/`resume`/`stop`/`crash`; `reason`: `operator`/`session_limit`/`auth_lost`/`repeated_failure`/`crash` | управление сеансом (`time.md#sessions`) |
| `input` | `sender`: `operator`/`stranger`; `text`; `channel` | приходит сообщение (`input.arrived`); `stranger` — неизвестный отправитель |
| `wait` | ровно одно из `life_ms`, `calendar_ms` (положительные) | проходит время жизни или календарное время (пауза) |
| `decide` | `situation` | **ключевое решение**: система должна принять решение (один цикл); `situation` — что ей предстоит выбрать |
| `model` | `proposal` (`attend`, `message`, `action`, `belief`, `memory`, `intention`, `reflection`, `request`, `other`), `delivery` (`once`, `twice`, `stale`, `after_restore`), `content` | заготовленный ответ поставщика интеллекта: доставить один раз, дважды, устаревшим по версии, из эпохи до восстановления |
| `world` | `outcome`: `confirmed`/`failed`/`no_answer`; `action` | мир сообщает результат действия |
| `operator` | `intervention` (вид из `permissions.md#interventions`), `reason`; `detail` | вмешательство оператора через панель (причина обязательна, `I-2`) |
| `fault` | `fault`: `auth_error`/`limit`/`lost_ack`/`disk_full`/`crash_during_action` | сбой в окружении |
| `backup` | `action`: `create`/`restore` | копия и восстановление |
| `provider` | `action = "swap"`, `to` | смена поставщика интеллекта |

В группах `experiments` и `motivation` в каждом прогоне должно быть от 1 до **4** шагов `decide` (шаги без `run` считаются во всех прогонах): это «не более четырёх ключевых решений» (`R-127`). Инструмент проверяет число.

## 6. Утверждения `[[assert]]`

Каждое: уникальный `id`, `kind`, `explain` (что проверяется и что означает провал), необязательные `run`, `class`. Окно во времени задают `after`/`before` — `id` шагов; без них — весь прогон.

| `kind` | Поля | Истинно, когда |
|---|---|---|
| `event` | `type`; `where`; `count` **или** `min`/`max` (без поля — «хотя бы одно») | в журнале число событий типа `type` с подходящим `payload` в нужных границах |
| `absent` | `type`; `where` | таких событий нет |
| `order` | `first`, `second` (типы) | первое такое событие по `seq` раньше второго |
| `chain` | `effect`, `caused_by` (типы) | событие `effect` достижимо по цепочке `causes` от события `caused_by` («прослеживаемое основание», `R-002`) |
| `state` | `path`, `op`, `value`; для `unchanged`/`changed` — `since`; необязательно `after` (момент проверки) | значение поля соответствует; `op`: `eq`, `ne`, `gt`, `ge`, `lt`, `le`, `in`, `contains`, `absent`, `unchanged`, `changed` |
| `text` | `marker`, `scope`, `presence`: `present`/`absent` | контрольная строка есть (нет) в области: `model_requests` (запросы к модели), `journal` (журнал и архив), `memory_retrieval` (результаты обычного извлечения), `state`, `outbound_messages` |
| `compare` | `runs` (два разных прогона), `subject`, `relation`: `differs`/`same` | предмет сравнения в двух прогонах различается (совпадает) |

Соглашения:

- **Типы событий** — только из каталога `docs/spec/events.md`; неизвестный тип инструмент отвергает.
- **`where`** — таблица «поле payload = значение»; значение `"*"` означает «поле присутствует и не пусто».
- **Путь состояния** начинается с группы состояния (`traits`, `affect`, `beliefs`, `relations`, `intentions`, `preferences`, `selfmodel`, `world_time`) либо `memory`; дальше — логические имена из предыстории или темы.
- **`subject`** в `compare`: `journal:<тип события>` (сравнивается payload принятых событий этого типа) или `state:<путь>`.
- **Контрольная строка** (`marker`) в сценариях о непрочитанном — уникальный токен вроде `ЗЕЛЁНЫЙ-ТИГР-42`; чтобы проверка не была пустой, добавляется `text … scope = "journal" presence = "present"` — сообщение действительно сохранено приёмником.
- **`class`**: `technical` (нарушение исключает вариант независимо от качества разговора, `R-133`) или `causal` (оценивается разработчиком отдельно, `R-136`). В группах `experiments` и `motivation` класс обязателен и должны быть утверждения обоих классов; в `required` все утверждения жёсткие, класс не нужен.

## 7. Метрики `[[metric]]`

Для `motivation` обязательна хотя бы одна (`R-132`: у каждого явления есть метрика), для `experiments` необязательны. Поля: `id`, `definition` (как считается по записям), `source` (`journal`, `state`, `trace`).

## 8. Что проверяет `tools/scenarios.py validate`

- форма каждого сценария (все поля выше, закрытые перечни значений, уникальность `id`, ссылки на шаги и прогоны, число ключевых решений);
- в каталоге ровно 19 + 8 + 6 сценариев; каждая из 19 строк таблицы §5.1 присутствует ровно в одном сценарии, и её тексты совпадают с планом дословно;
- все `requirements` существуют; связь с реестром **двусторонняя**: требование, перечисленное в сценарии, ссылается на файл сценария в своём `check`, а ссылка на `scenarios/…toml` в `check` указывает на существующий сценарий, который это требование перечисляет;
- каждое требование `kind = functional` имеет сценарий либо тест/прогон в тексте `check` (`coverage` показывает разбивку).

Что инструмент **не** проверяет: правильность самого ожидания (смысл утверждений проверяет человек при ревью) и выполнимость на конкретной системе — сценарии исполняются позже, в S11 (стенд) и S25 (интеграция); пока ни одно требование не получает статус `verified` по самому факту существования сценария.

## 9. Как добавить сценарий

1. Скопировать подходящий файл, изменить `id`, `title`, `summary`, `requirements`, `failure`.
2. Описать шаги и утверждения через наблюдаемое (журнал/состояние/текст в областях), к каждому — `explain`.
3. В `check` каждого перечисленного требования добавить путь к файлу.
4. `python3 tools/scenarios.py validate && python3 tools/reqs.py validate`.
