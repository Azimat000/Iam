# Спецификация: конверты запроса и ответа модели

Статус: S02. Источник: `docs/PLAN.md` §2.8, §3.1, §5.1–§5.3. Схемы: `schemas/request.schema.json`, `schemas/response.schema.json`, `schemas/proposal.schema.json`. Реализация — `iam.interfaces.CognitiveProvider` (S07), `iam.state` (S05).

Цикл: **событие → внимание → извлечение памяти → оценка → предложение решения → проверка ядром → действие → подтверждённый результат → обновление памяти.** Модель участвует только в шагах оценки и предложения; всё остальное делает ядро.

## 1. Запрос {#request}

Требования: R-107, R-104, R-207, R-039

Поля запроса (`request.schema.json`):

| Поле | Смысл |
|---|---|
| `request_id` | `req_…`, уникален |
| `persona_id`, `session_id` | к кому и в каком сеансе |
| `state_version` | версия состояния, на основе которой собран контекст |
| `issued_at`, `life_time_ms` | календарное время и время жизни |
| `purpose` | вид задачи: `appraise`, `choose_action`, `compose_message`, `reflect`, `summarize`, `generalize` |
| `context` | элементы контекста, каждый с `ref`, `origin`, `layer`; **только прочитанное** и доступное из памяти |
| `allowed_proposals` | какие виды предложений допустимы; `allowed_actions` — возможности со статусом `available` |
| `limits` | `max_output_tokens`, `deadline_ms`, `attempt` (номер попытки, 0 или 1) |
| `response_schema` | ссылка на схему ответа |
| `idempotency_key` | `req:<request_id>` |

Правила:

- **E-1.** Контекст собирает только ядро и только из допустимых источников: прочитанные элементы (`input.read`), записи слоёв `personal`/`interpretation`, состояние. Архив, непрочитанное, секреты, токены, пути хранилища **не включаются**.
- **E-2.** В облачную модель передаются только необходимые фрагменты (минимум данных).
- **E-3.** Запрос записывается событием `proposal.requested` до отправки.

## 2. Ответ {#response}

Требования: R-107, R-117, R-091

Поля ответа: `request_id` (эхо), `state_version` (эхо), `provider` (`{name, model}`), `status` (`ok | refused | error`), `proposals[]`, `explanation` (текст, хранится как `model_explanation`), `usage` (`{calls, duration_ms}`), `tool_use_detected` (bool).

- **E-4.** Ответ без эха `request_id` и `state_version` отклоняется.
- **E-5.** Ответ записывается событием `proposal.received` (ключ `resp:<request_id>`), даже если не применяется.
- **E-6.** Если `tool_use_detected = true`, результат непригоден для изменения личности (`R-117`): ничего из `proposals[]` не применяется, пишется `proposal.rejected` с причиной и событие `system.error`.
- **E-7.** Ответ с неверным форматом: не более **одной** повторной попытки исправления (`attempt` 0 → 1), затем отклонение (`R-194`).

## 3. Предложение решения {#proposal}

Требования: R-104, R-199, R-222, R-097

Модель возвращает **предложения**; применяет их ядро. Поля: `proposal_id`, `kind`, `rationale` (текст-объяснение), `cites[]` (ссылки на записи, на которые опирается), `body` (по виду).

| `kind` | Смысл | `body` |
|---|---|---|
| `action` | выполнить действие в мире | `{capability_id, params, expected_duration_ms}` |
| `message` | отправить сообщение собеседнику | `{to, text}` |
| `state_change` | изменить поле состояния | `{ops[]}` как в `state.md#versioning` |
| `memory_write` | запомнить/пересмотреть | `{draft}` (черновик записи, `origin` указан) |
| `intention` | создать/перевести намерение | `{op, intention_id?, text?, to_status?}` |
| `creator_request` | просьба оператору | `{request_key, text}` |
| `no_action` | отдых/бездействие | `{reason}` |

Правила:

- **E-8.** Предложение **не есть** событие, воспоминание или выполненное действие. Пока нет `action.confirmed`, воспоминание «я сделала» не создаётся.
- **E-9.** Ядро проверяет каждое предложение: версия, права (`permissions.md#three-states`), инварианты состояния, происхождение (запрещено выдавать `imagination` за результат), лимиты. Результат: `proposal.accepted` (и переход состояния) либо `proposal.rejected` (с причиной).
- **E-10.** Одно предложение — один переход; принимается целиком или отклоняется.

## 4. Устаревание ответа {#staleness}

Требования: R-108, R-183, R-107

Ответ применяется, только если **одновременно**:

1. `response.state_version == current_state_version` (в момент применения);
2. `request_id` известен ядру и ещё не обработан (нет события `resp:<request_id>` с применением);
3. сеанс всё ещё `running` и принадлежит тому же `session_id`;
4. не истёк `deadline_ms`.

Иначе — событие `proposal.stale` (если нарушены 1–2, 4) или `proposal.rejected` (если нарушены права/инварианты); состояние не меняется. «Молчаливой перебазировки» нет: ядро не пытается применить устаревшее предложение к новой версии; при необходимости цикл формирует новый запрос с новой версией.

Повторный приход того же ответа (повтор результата, «старый ответ») применяется **не более одного раза**: дедупликация по `resp:<request_id>` (`events.md#idempotency`).
Поступление сообщения в паузе (`input.arrived`, `changes_state = false`) версию не меняет и не просрочивает ответ.

## 5. Подтверждение результата {#confirmation}

Требования: R-199, R-222, R-184

После принятия предложения вида `action`/`message` ядро пишет `action.attempted`. Исход фиксируется **только** событием от подтверждающего источника: `action.confirmed`, `action.failed` или (если подтверждения нет) `action.unknown_outcome`/`message.out_unknown`. Только после `action.confirmed` создаётся воспоминание о выполненном действии и обновляется мир. Сбой во время действия не объявляется успехом (`R-184`).
